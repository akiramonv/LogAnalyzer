# Конфигурация и правила

Конфигурация — один YAML- или JSON-файл, подключается ключом `-c`:

```bash
log-analyzer analyze -i app.log -c analyzer.yaml
```

Все секции необязательны: отсутствующие берут значения по умолчанию.
Готовый образец со всеми параметрами — [`analyzer.example.yaml`](../analyzer.example.yaml).

## Секция `parse` — разбор логов

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `charset` | `UTF-8` | Кодировка файлов логов. |
| `zone` | системная | Часовой пояс для форматов без смещения (`2026-08-09 10:00:00`). |
| `defaultDate` | сегодня | Дата для логов, где есть только время (дефолтный шаблон Logback `%d{HH:mm:ss.SSS}`). |
| `patterns` | — | Свои шаблоны строк: `name` + `regex`. Применяются **раньше** встроенных. |
| `builtinPatterns` | `true` | Использовать встроенные шаблоны. |
| `extractFromMessage` | `true` | Искать `traceId=`, `sessionId=`, `duration=` и HTTP-признаки внутри текста сообщения. |
| `maxEvents` | `0` (без ограничения) | Предел числа событий на источник. |
| `maxMultilineLines` | `2000` | Предел строк в одном многострочном блоке. |

### Именованные группы в своём шаблоне

| Группа | Смысл |
|---|---|
| `ts` | Метка времени |
| `level` | Уровень |
| `thread` | Имя потока |
| `logger` | Логгер/категория |
| `msg` | Текст сообщения |
| `trace` | `traceId` или `traceId,spanId` |
| `sleuth` | Блок Sleuth: `app,traceId,spanId,exportable` |
| `app` | Имя сервиса |
| `pid` | Идентификатор процесса |

Обязательна только `msg`. Проверить шаблон:

```bash
log-analyzer patterns --test "строка лога" --regex '^(?<ts>\S+) (?<level>\w+) (?<msg>.*)$'
```

## Секция `correlation` — сборка событий в инциденты

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `priority` | `[TRACE, REQUEST, SESSION, THREAD]` | Какие признаки использовать. Уберите `SESSION`, если сессия слишком широкая. |
| `threadGapSeconds` | `30` | Пауза, после которой события одного потока считаются разными инцидентами. |
| `inheritTraceFromThread` | `true` | Приписывать строки без `traceId` к активной цепочке того же потока. |
| `inheritWindowSeconds` | `10` | Окно, в пределах которого работает наследование. |
| `additionalKeys` | — | Свои бизнес-ключи из MDC/атрибутов: `orderId`, `paymentId`, … |
| `fallbackToFile` | `true` | Если признаков нет вообще — собирать события источника в один таймлайн. |
| `minEventsPerTimeline` | `0` | Отбрасывать короткие цепочки (кроме тех, где есть ошибки). |

## Секция `timeline` — построение таймлайна

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `dedup` | `true` | Схлопывать идущие подряд одинаковые события. |
| `dedupNormalize` | `true` | При сравнении заменять числа, UUID и hex на плейсхолдеры — так серия ретраев схлопывается в одну строку. |
| `dedupWindowSeconds` | `300` | Максимальный интервал между схлопываемыми повторами. |
| `slowMs` | `1000` | Порог, выше которого операция помечается как медленная. |
| `linkHttp` | `true` | Связывать HTTP-запрос с ответом. |
| `suspiciousGapSeconds` | `5` | Пауза между событиями, которая сама по себе подозрительна. |

## Секция `rules` — правила

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `builtin` | `true` | Подключать встроенный набор (55 правил). |
| `files` | — | Пути к своим файлам правил. |

## Секция `analysis` — вывод о причине

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `minConfidence` | `0.3` | Гипотезы ниже порога не попадают в отчёт. |
| `maxAlternatives` | `3` | Сколько альтернативных версий сохранять. |
| `applicationPackages` | — | Пакеты вашего кода: помогают найти «своё» место в стеке вместо кадров фреймворка. **Стоит заполнить** — заметно улучшает формулировку причины. |
| `detectCascade` | `true` | Учитывать каскад ошибок и пусковые события. |

# Формат правил

Файл правил — YAML или JSON:

```yaml
name: my-rules
description: Правила для платёжного сервиса
rules:
  - name: payment-declined       # обязательное уникальное имя
    description: Банк отклонил операцию
    enabled: true                # можно временно выключить
    priority: 80                 # больше — раньше применяется
    when: { ... }                # условие (обязательно, непустое)
    precededBy: { ... }          # необязательное условие по предыдущим событиям
    annotate: [ ... ]            # пометки на событии
    cause: { ... }               # гипотеза о причине
    stopOnMatch: false           # не применять остальные правила к этому событию
```

## Блок `when`

Все заданные поля объединяются по «И»; списки внутри поля — по «ИЛИ».

| Поле | Тип | Что проверяет |
|---|---|---|
| `messageRegex` | regex | Текст события: сообщение + заголовки исключений + сводка HTTP. |
| `anyMessageRegex` | список regex | Хотя бы одно совпадение. |
| `exceptionType` | regex | Имя класса исключения **в любом звене цепочки** `Caused by`. |
| `exceptionMessageRegex` | regex | Сообщение исключения в любом звене. |
| `loggerRegex` | regex | Имя логгера. |
| `threadRegex` | regex | Имя потока. |
| `levelAtLeast` | уровень | Минимальный уровень: `TRACE`…`FATAL`. |
| `level` | уровень | Точный уровень. |
| `kind` | `LOG`, `EXCEPTION`, `HTTP_REQUEST`, `HTTP_RESPONSE`, `UNPARSED` | Тип события. |
| `httpStatus` | список чисел | Конкретные HTTP-статусы. |
| `httpStatusClass` | `1xx`…`5xx` | Класс статусов. |
| `attributes` | `ключ: regex` | Значения атрибутов и MDC. |
| `minDurationMs` | число | Минимальная длительность операции. |
| `caseSensitive` | `false` | Учитывать регистр в регулярных выражениях. |

## Блок `precededBy`

```yaml
precededBy:
  withinSeconds: 120   # 0 — искать по всему таймлайну
  when:
    anyMessageRegex: ['Retry attempt', 'attempt \d+ of \d+']
```

Правило сработает, только если раньше в этой же цепочке встретилось подходящее событие.

## Блок `annotate`

```yaml
annotate:
  - type: TIMEOUT
    label: Таймаут платёжного шлюза
```

Доступные типы: `EXCEPTION`, `ERROR`, `WARNING`, `RETRY`, `EXTERNAL_CALL`, `TIMEOUT`, `SLOW`,
`DATABASE`, `MESSAGING`, `CACHE`, `SECURITY`, `CONFIGURATION`, `RESOURCE`, `RESILIENCE`,
`TRANSACTION`, `VALIDATION`, `HTTP_CLIENT_ERROR`, `HTTP_SERVER_ERROR`, `LIFECYCLE`, `INFO`.

## Блок `cause`

```yaml
cause:
  title: Платёж отклонён банком-эмитентом
  description: >-
    Шлюз вернул отказ на стороне банка: операция дошла до эмитента и была им не одобрена.
    Повтор того же запроса не поможет — решение принимает банк держателя карты.
  category: integration
  confidence: 0.85          # 0..1
  recommendation: Проверьте код отказа в ответе шлюза и лимиты карты.
  steps:                    # пошаговый план: попадает в отчёт нумерованным списком
    - >-
      Найдите код отказа в ответе шлюза — он определяет, можно ли повторять операцию.
    - >-
      Проверьте лимиты и статус карты на стороне эмитента.
    - >-
      Убедитесь, что клиенту показано понятное сообщение, а не техническая ошибка.
```

> В YAML элементы `steps` удобно писать блочными скалярами (`- >-`): тогда внутри текста
> можно свободно использовать двоеточия и кавычки.

`confidence` — базовая уверенность правила. Итоговая корректируется анализатором:
повышается, если правило сработало на первой ошибке цепочки, понижается для события,
которое ошибкой не является, и умножается на надёжность признака корреляции.

## Практические советы

- **Начните со встроенных правил:** `log-analyzer rules --export my-rules.yaml`, затем правьте.
- **Проверяйте сразу:** `log-analyzer rules --validate my-rules.yaml`.
- Специфичным правилам ставьте больший `priority`, чем общим: правило про HikariCP должно
  идти раньше общего правила про `SQLException`.
- Правило без `cause` — просто пометка на таймлайне: это нормально и полезно
  (например, для `retry-attempt`).
- Не завышайте `confidence`: 0.9+ уместно, когда формулировка почти наверняка верна.
